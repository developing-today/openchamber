# Auto Model Routing

Pick **Auto** in the model picker and OpenChamber chooses the model for every prompt you send. A typo fix goes to a cheap, fast model; a tricky bug goes to your strongest one. You decide which model handles which kind of task, once, in Settings.

## Turn it on

1. Make sure a [classification provider](/classification-providers/) is set up. Auto needs Jev to sort prompts.
2. Open **Settings → Routing** and check **Enable Auto mode**.
3. Choose a **Fallback model** (and its thinking level). Auto stays hidden until you do.
4. Look through the categories below and give the ones you care about their own model.

When everything is in place, the page says **Ready**. Pick **Auto** at the top of the model picker in any session.

## Categories

Every prompt lands in one category. Five come built in:

| Category | For |
| --- | --- |
| Trivial | mechanical work: renames, typos, formatting, comments, simple commands |
| Research | reading and explaining code without changing it |
| Implement | a clear change: a feature with a known shape, tests, a fix whose cause is known |
| Review | inspect changes for correctness, regressions, security issues and missing tests; report findings without editing |
| Hard | bugs with an unknown cause, design and planning, security, auth, concurrency, migrations, money |

For each category you can set:

- **Model:** empty means the fallback model
- **Thinking:** the thinking level for that model
- **Agent:** the agent that runs these tasks; empty keeps the agent the composer would use

## Auto stays on a model across similar prompts

Jev classifies every prompt on its own, so two similar follow-ups can land in
neighbouring categories. To keep a session from bouncing between models (and
losing the provider's prompt cache each time), Auto holds the session's model
unless the evidence for a change is consistent:

- Leaving the model a session started on takes two prompts in a row that point
  at the same other model, or one prompt Jev is sure about.
- After a jump to a stronger model, the session stays there until three prompts
  in a row point elsewhere. A sure answer shortens that, but never below two.
- A prompt Jev cannot place (low confidence, unknown category, Jev unreachable)
  keeps the current model. The fallback model only serves a session with no
  history yet.

The routing decision shows `held` when Auto kept the model against Jev's latest
answer. That history lives in the server process, so a restart starts sessions
fresh. Whether a session is on Auto is saved, so a restart keeps it on Auto
until you choose a real model.

In **Settings → Routing**, turn **Stay on the current model** off to follow every
prompt, or change **Prompts to switch** and **Prompts to switch back**. The
confidence that counts as "sure" is `stickiness.strongConfidence` in
`routing.json` (default 0.9).

## Use provider pools for category models

OpenChamber chooses the category, thinking level and agent. OpenCode owns
provider failover. Define ordered pools in OpenCode's
`experimental.model_routes`, then choose the route model for a category. For
example, set **Trivial** to `opencode-route/cheap-fast`, **Implement** to
`opencode-route/smart-slow`, and **Hard** and **Review** to
`opencode-route/frontier-heavy`. Jev still makes the task decision; the chosen
route then tries its providers in order.

OpenCode moves to another target on retryable provider failures, quota or
authentication errors, and a missed first-output deadline. Completed requests
can also mark a target degraded using the configured latency or throughput
thresholds. Cooldowns are shared by sessions in the OpenCode process and restored after a
restart, and OpenCode records every routing decision, attempt (exact error
code and message, timings, token counts) and cooldown in its database for later
analysis. A turn is never replayed after any answer or tool output has started.

OpenCode also reads each response's rate-limit headers and moves traffic off a
target whose provider says its window is spent, before the provider starts refusing it.

A pool can also make several requests to a target before moving on (`attempts`,
two in total by default), start the next target when the first is silent
(`hedgeAfterMs`), cap a target's requests and tokens (`budgets`, which count every
request OpenCode makes to the target, background ones such as titles included),
and be tuned by the agent from its recorded history. These are OpenCode route
options; see its configuration reference.

### See which sessions share a target

When a target's plan runs out, every session on that target fails over at once
and each starts again with a cold prompt cache. **Settings → Routing → Model
pools → Pool health** shows, for each target in each pool, how many sessions
used it in the last 15 minutes, and warns when two or more share it.

Link a target to one of your plans there to see a projection: its recent usage,
together with every other target linked to the same plan, scaled to the plan's
quota window. Windows counted in requests, messages or tokens get a projection;
dollar and percent windows don't. The figure is an estimate from the last 24
hours of OpenCode traffic and can't see usage from outside OpenCode. In a
weighted or round-robin pool, a target at 70% or more of its window gets a
**Lower weight** button that halves its weight, so new sessions lean toward the
other targets.

Jev sorts prompts by reading the category names and descriptions, so the descriptions work as instructions. Say what belongs in the category and what doesn't. You can edit, turn off, remove or add categories, and restore a built-in one if you change your mind. Auto needs at least two categories turned on.

## What happens when you send

1. OpenChamber sends your message and a short excerpt of the last few turns to Jev.
2. Jev picks a category and says how sure it is.
3. The session switches to that category's model, thinking level and agent, and your message goes out.

Every message is sorted again, so a session can move from a cheap model for a quick question to your strongest one for the next request. The composer keeps showing **Auto**, and the agent and thinking controls are hidden, because the category decides them.

The fallback model answers when:

- Jev isn't sure enough (below 60% confidence)
- Jev fails or takes longer than four seconds
- the category has no model of its own

Choosing any real model in the picker takes the session out of Auto. Pick **Auto** again to come back. You can also make Auto the default for new sessions in **Settings → Sessions**.

## Plans, usage and reviews

**Settings → Routing → Plans and usage** keeps what the review cannot measure: your subscriptions and their quota windows (name, unit, limit, how long the window is, how it resets), fees and expiry dates, the date each plan was last checked and where from, a cost tier for each model (`plan`, `common`, `medium`, `high`, with the plans that cover it), what each pool is for, and notes about how usage has felt. Notes are kept as you wrote them and never rewritten. Use them for things like "ran out of Claude too fast" or "I always have GPT left at month end"; the review weighs them against the usage history.

Two buttons start a new chat with a command ready to send:

- **Review routing** runs `/routing-review`. It reads the route history (requests, tokens, cost, sessions, and which pools used or skipped each provider and model), the plan records and the notes, and proposes changes. It changes nothing until you approve a specific change.
- **Update plans** runs `/plan-update`. It finds plans that are missing details or were last checked more than a month ago, asks for the few fields it needs, and records your answers.

The records live in OpenCode's data directory as `plans.json` and `plan-notes.jsonl`, and nothing in them expires. The history is kept too; `route_usage` can read any window of it.

## Where it works

Auto runs in the OpenChamber server: the desktop app, the web app, and your phone connected to either. VS Code doesn't offer Auto, because the extension talks to OpenCode directly.
