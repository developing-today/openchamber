# 자동 모델 라우팅

모델 선택기에서 **자동**을 고르면 보내는 프롬프트마다 OpenChamber가 모델을 고릅니다. 오타 수정은 싸고 빠른 모델로, 까다로운 버그는 가장 강한 모델로 갑니다. 어떤 모델이 어떤 종류의 작업을 맡을지는 설정에서 한 번만 정하면 됩니다.

## 켜기

1. [분류 제공자](/ko/classification-providers/)가 설정되어 있는지 확인합니다. Auto는 프롬프트를 분류할 때 Jev를 씁니다.
2. **설정 → 라우팅**을 열고 **Auto 모드 사용**을 켭니다.
3. **대체 모델**(과 사고 수준)을 고릅니다. 고르기 전까지 Auto는 숨겨져 있습니다.
4. 아래 카테고리를 살펴보고, 중요한 카테고리에는 전용 모델을 지정합니다.

모든 준비가 끝나면 페이지에 **준비됨**이 표시됩니다. 어느 세션에서든 모델 선택기 맨 위의 **자동**을 고르세요.

## 카테고리

모든 프롬프트는 카테고리 하나에 들어갑니다. 기본 제공 카테고리는 다섯 개입니다.

| 카테고리 | 대상 |
| --- | --- |
| Trivial | 기계적인 작업: 이름 바꾸기, 오타, 서식, 주석, 간단한 명령 |
| Research | 코드를 바꾸지 않고 읽고 설명하기 |
| Implement | 분명한 변경: 범위가 정해진 기능, 테스트, 원인을 아는 수정 |
| Review | 변경 사항을 정확성, 회귀, 보안 문제, 빠진 테스트 관점에서 검사하고, 편집하지 않고 결과를 보고하기 |
| Hard | 원인을 모르는 버그, 설계와 계획, 보안, 인증, 동시성, 마이그레이션, 돈 관련 로직 |

카테고리마다 다음을 설정할 수 있습니다.

- **모델:** 비워 두면 대체 모델
- **사고:** 그 모델의 사고 수준
- **에이전트:** 이 작업을 실행할 에이전트. 비워 두면 입력창에서 쓰는 에이전트를 유지

## 비슷한 프롬프트에서는 같은 모델 유지

Jev는 프롬프트를 하나씩 분류하므로 비슷한 후속 프롬프트 두 개가 이웃한 카테고리에 들어갈 수 있습니다. 세션이 모델 사이를 오가며(그때마다 제공자의 프롬프트 캐시까지 잃으며) 흔들리지 않도록, Auto는 변경 근거가 한결같아질 때까지 세션의 모델을 유지합니다.

- 세션이 시작한 모델을 벗어나려면 같은 다른 모델을 가리키는 프롬프트가 두 번 연속 나오거나, Jev가 확신하는 프롬프트가 한 번 나와야 합니다.
- 더 강한 모델로 뛰어오른 뒤에는 다른 곳을 가리키는 프롬프트가 세 번 연속 나올 때까지 세션이 거기 머뭅니다. 확신하는 답이 나오면 짧아지지만 두 번 아래로는 내려가지 않습니다.
- Jev가 분류하지 못하는 프롬프트(낮은 확신, 알 수 없는 카테고리, Jev에 닿지 않음)는 현재 모델을 유지합니다. 대체 모델은 아직 기록이 없는 세션에만 쓰입니다.

Auto가 Jev의 최신 답과 다르게 모델을 유지하면 라우팅 결정에 `held`라고 표시됩니다. 이 기록은 서버 프로세스 안에 있으므로 재시작하면 세션이 새로 시작됩니다. 세션이 Auto인지는 저장되므로, 실제 모델을 고르기 전까지 재시작해도 Auto로 남습니다.

**설정 → 라우팅**에서 **현재 모델 유지**를 끄면 모든 프롬프트를 따르고, **전환까지의 프롬프트 수**와 **되돌아가기까지의 프롬프트 수**를 바꿀 수 있습니다. '확신'으로 치는 확신도는 `routing.json`의 `stickiness.strongConfidence`입니다(기본값 0.9).

## 카테고리 모델에 제공자 풀 사용

카테고리, 사고 수준, 에이전트는 OpenChamber가 고릅니다. 제공자 장애 전환은 OpenCode가 맡습니다. OpenCode의 `experimental.model_routes`에 순서 있는 풀을 정의한 뒤 카테고리의 라우트 모델을 고르세요. 예를 들어 **Trivial**은 `opencode-route/cheap-fast`로, **Implement**는 `opencode-route/smart-slow`로, **Hard**와 **Review**는 `opencode-route/frontier-heavy`로 설정합니다. 작업 판단은 여전히 Jev가 하고, 선택된 라우트가 그다음 제공자를 순서대로 시도합니다.

OpenCode는 재시도 가능한 제공자 실패, 쿼터나 인증 오류, 첫 출력 기한을 놓쳤을 때 다른 대상으로 이동합니다. 완료된 요청도 설정된 지연이나 처리량 임계값으로 대상을 성능 저하로 표시할 수 있습니다. 쿨다운은 OpenCode 프로세스 안의 세션끼리 공유되고 재시작 뒤 복원되며, OpenCode는 모든 라우팅 결정, 시도(정확한 오류 코드와 메시지, 시간, 토큰 수), 쿨다운을 나중에 분석할 수 있도록 데이터베이스에 기록합니다. 답변이나 도구 출력이 시작된 뒤에는 그 턴을 다시 실행하지 않습니다.

OpenCode는 각 응답의 속도 제한 헤더도 읽어서, 제공자가 기간을 다 썼다고 말한 대상에서는 제공자가 거부를 시작하기 전에 트래픽을 빼냅니다.

풀은 다음으로 넘어가기 전에 대상에 여러 번 요청하거나(`attempts`, 기본값은 총 두 번), 첫 대상이 침묵하면 다음 대상을 시작하거나(`hedgeAfterMs`), 대상의 요청과 토큰에 상한을 두거나(`budgets`, 제목 같은 백그라운드 요청까지 포함해 OpenCode가 그 대상에 보내는 모든 요청을 셉니다), 기록된 이력을 바탕으로 에이전트가 조정하게 할 수도 있습니다. 이들은 OpenCode 라우트 옵션이니 구성 레퍼런스를 보세요.

일정은 정해 둔 요일이나 시각에 대상의 가중치를 바꿉니다. 예를 들어 제공자의 피크 시간에 그 제공자로 가는 트래픽을 줄일 수 있습니다. 풀마다의 일정은 **설정 → 라우팅 → 모델 풀**에서 각 풀의 고급 옵션 안에 있고, 풀 목록 아래의 **모든 풀에 적용되는 일정**은 모든 풀 또는 지정한 풀에서만 일치하는 대상을 바꿉니다. 일정마다 요일, 날짜, 시작 시각과 종료 시각, 시간대, 그리고 가중치에 곱할 배수나 가중치를 대신할 값 중 하나를 지정합니다. 적용 시간 밖에서는 설정한 가중치가 쓰입니다. OpenCode는 프로젝트의 `opencode.json` 같은 다른 설정 파일에 있는 일정도 적용합니다. 설정에서는 이런 일정을 읽기 전용으로, 편집할 파일 이름 아래에 보여 줍니다.

각 풀은 무엇을 위한 것인지도 말할 수 있습니다. **설정 → 라우팅 → 모델 풀**에서 풀을 열고 **설명**에 «여러 파일에 걸친 긴 리팩터링; 느림; 비용이 가장 많이 듦» 같은 한 줄을, **세부 정보**에 그 풀을 언제 쓰고 언제 쓰지 말지를 적은 문단을 채우세요. 카테고리의 모델이 풀이면 Jev는 그 카테고리의 설명과 함께 둘 다 읽습니다. OpenChamber는 이들을 `opencode.json`의 라우트에 `description`과 `details`로 저장합니다. OpenCode는 이 두 키를 무시하므로, 파일을 OpenCode의 JSON 스키마로 검사하는 편집기는 경고를 표시할 수 있습니다.

Jev는 카테고리의 이름과 설명을 읽고 프롬프트를 분류하므로, 설명이 지시문 역할을 합니다. 카테고리에 들어가는 것과 들어가지 않는 것을 적어 두세요. 카테고리는 수정, 끄기, 삭제, 추가가 가능하고, 마음이 바뀌면 기본 카테고리를 복원할 수 있습니다. Auto를 쓰려면 켜진 카테고리가 두 개 이상 있어야 합니다.

### 어떤 세션이 대상을 함께 쓰는지 보기

대상의 플랜이 바닥나면 그 대상에 있는 모든 세션이 한꺼번에 다음 대상으로 넘어가고, 각 세션은 빈 프롬프트 캐시로 다시 시작합니다. **설정 → 라우팅 → 모델 풀 → 풀 상태**는 각 풀의 대상마다 최근 15분 동안 그 대상을 쓴 세션 수를 보여 주고, 두 개 이상의 세션이 함께 쓰면 경고합니다.

여기서 대상을 내 플랜 중 하나에 연결하면 예측을 볼 수 있습니다. 그 대상의 최근 사용량을 같은 플랜에 연결된 다른 모든 대상의 사용량과 합쳐 플랜의 쿼터 기간에 맞춰 환산한 값입니다. 요청, 메시지, 토큰으로 세는 기간에는 예측이 나오고, 달러나 퍼센트로 세는 기간에는 나오지 않습니다. 이 수치는 최근 24시간의 OpenCode 트래픽으로 낸 추정치이며 OpenCode 밖에서 쓴 양은 알 수 없습니다. 가중치 방식이나 라운드 로빈 방식의 풀에서는 기간의 70% 이상에 도달한 대상에 **가중치 낮추기** 버튼이 생깁니다. 이 버튼은 가중치를 절반으로 줄여 새 세션이 다른 대상으로 더 많이 가도록 합니다.

## 보낼 때 일어나는 일

1. OpenChamber가 메시지와 최근 몇 턴의 짧은 발췌를 Jev에 보냅니다.
2. Jev가 카테고리를 고르고 얼마나 확신하는지 알려 줍니다.
3. 세션이 그 카테고리의 모델, 사고 수준, 에이전트로 바뀌고 메시지가 전송됩니다.

메시지마다 다시 분류하므로, 간단한 질문에는 싼 모델을 쓰다가 다음 요청에서는 가장 강한 모델로 바뀔 수 있습니다. 입력창에는 계속 **자동**이 표시되고, 에이전트와 사고 수준 선택은 숨겨집니다. 둘 다 카테고리가 정하기 때문입니다.

다음 경우에는 대체 모델이 답합니다.

- Jev의 확신이 부족할 때(60% 미만)
- Jev가 실패하거나 4초보다 오래 걸릴 때
- 카테고리에 전용 모델이 없을 때

선택기에서 특정 모델을 고르면 그 세션은 Auto에서 빠집니다. 돌아가려면 다시 **자동**을 고르세요. **설정 → 세션**에서 새 세션의 기본값을 Auto로 정할 수도 있습니다.

## 플랜, 사용량, 검토

**설정 → 라우팅 → 플랜 및 사용량**은 검토가 측정할 수 없는 것을 보관합니다. 구독과 그 쿼터 기간(이름, 단위, 한도, 기간 길이, 재설정 방식), 요금과 만료일, 각 플랜을 마지막으로 확인한 날짜와 확인 위치, 모델마다의 비용 등급(`plan`, `common`, `medium`, `high`와 이를 포함하는 플랜), 각 풀이 무엇을 위한 것인지, 사용해 본 느낌에 대한 메모가 그것입니다. 메모는 쓴 그대로 보관되고 다시 쓰이지 않습니다. «Claude가 너무 빨리 바닥났다»거나 «월말이면 항상 GPT가 남는다» 같은 것을 적어 두세요. 검토는 사용 이력과 견주어 메모를 따져 봅니다.

버튼 두 개는 보낼 준비가 된 명령과 함께 새 채팅을 시작합니다.

- **라우팅 검토**는 `/routing-review`를 실행합니다. 라우트 이력(요청, 토큰, 비용, 세션, 어떤 풀이 어떤 제공자와 모델을 썼거나 건너뛰었는지), 플랜 기록, 메모를 읽고 변경을 제안합니다. 구체적인 변경을 승인하기 전에는 아무것도 바꾸지 않습니다.
- **플랜 업데이트**는 `/plan-update`를 실행합니다. 세부 정보가 빠졌거나 마지막 확인이 한 달보다 오래된 플랜을 찾고, 필요한 몇 가지 항목을 물은 뒤 답을 기록합니다.

기록은 OpenCode의 데이터 디렉터리에 `plans.json`과 `plan-notes.jsonl`로 보관되며, 그 안의 어떤 것도 만료되지 않습니다. 이력도 보관되며, `route_usage`가 그 어느 기간이든 읽을 수 있습니다.

## 사용할 수 있는 곳

Auto는 OpenChamber 서버에서 동작합니다. 데스크톱 앱, 웹 앱, 그리고 둘 중 하나에 연결된 휴대폰에서 쓸 수 있습니다. VS Code 확장은 OpenCode와 직접 통신하므로 Auto를 제공하지 않습니다.
