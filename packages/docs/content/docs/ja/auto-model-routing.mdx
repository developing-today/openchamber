# 自動モデルルーティング

モデル選択で **自動** を選ぶと、送信するプロンプトごとに OpenChamber がモデルを選びます。誤字の修正は安くて速いモデルへ、厄介なバグはいちばん強いモデルへ。どの種類のタスクをどのモデルに任せるかは、設定で一度決めるだけです。

## オンにする

1. [分類プロバイダー](/ja/classification-providers/)が設定されていることを確認します。Auto はプロンプトの振り分けに Jev を使います。
2. **設定 → ルーティング** を開き、**Auto モードを有効にする** にチェックを入れます。
3. **フォールバックモデル**（とその思考レベル）を選びます。選ぶまで Auto は表示されません。
4. 下のカテゴリを確認し、大事なものには専用のモデルを割り当てます。

すべて揃うと、ページに **準備完了** と表示されます。どのセッションでも、モデル選択の先頭にある **自動** を選んでください。

## カテゴリ

プロンプトはどれか 1 つのカテゴリに入ります。組み込みのカテゴリは 5 つです。

| カテゴリ | 対象 |
| --- | --- |
| Trivial | 機械的な作業：名前の変更、誤字、整形、コメント、簡単なコマンド |
| Research | コードを変えずに読んで説明する |
| Implement | 明確な変更：範囲がはっきりした機能、テスト、原因がわかっている修正 |
| Review | 変更を正確さ、リグレッション、セキュリティの問題、不足しているテストの観点で点検し、編集せずに結果を報告する |
| Hard | 原因不明のバグ、設計と計画、セキュリティ、認証、並行処理、移行、お金の処理 |

カテゴリごとに次を設定できます。

- **モデル：** 空欄ならフォールバックモデル
- **思考：** そのモデルの思考レベル
- **エージェント：** このタスクを実行するエージェント。空欄なら入力欄で使われるエージェントのまま

## 似たプロンプトでは同じモデルに留まる

Jev はプロンプトを 1 つずつ振り分けるので、似たフォローアップが隣り合うカテゴリに入ることがあります。セッションがモデル間を行ったり来たりして（そのたびにプロバイダーのプロンプトキャッシュも失って）しまわないよう、Auto は変更の根拠が一貫するまでセッションのモデルを保持します。

- セッションが最初に使ったモデルから離れるには、同じ別のモデルを指すプロンプトが 2 回続くか、Jev が確信を持てるプロンプトが 1 回必要です。
- より強いモデルへジャンプした後は、別の場所を指すプロンプトが 3 回続くまでセッションはそこに留まります。確信のある回答があると短くなりますが、2 回未満にはなりません。
- Jev が振り分けられないプロンプト（確信度が低い、カテゴリ不明、Jev に届かない）は現在のモデルを維持します。フォールバックモデルが使われるのは、まだ履歴のないセッションだけです。

Auto が Jev の最新の回答に反してモデルを保持した場合、ルーティングの決定には `held` と表示されます。この履歴はサーバープロセスの中にあるため、再起動するとセッションは新規の状態から始まります。セッションが Auto かどうかは保存されるため、再起動しても、実際のモデルを選ぶまでは Auto のままになります。

**設定 → ルーティング** で **現在のモデルを維持** をオフにするとすべてのプロンプトに従います。**切り替えまでのプロンプト数** と **戻るまでのプロンプト数** も変更できます。「確信あり」とみなす確信度は `routing.json` の `stickiness.strongConfidence` です（既定値は 0.9）。

## カテゴリモデルにプロバイダープールを使う

カテゴリ、思考レベル、エージェントを選ぶのは OpenChamber です。プロバイダーのフェイルオーバーは OpenCode が担います。OpenCode の `experimental.model_routes` に順序付きのプールを定義し、カテゴリごとにルートモデルを選びます。たとえば、**Trivial** に `opencode-route/cheap-fast`、**Implement** に `opencode-route/smart-slow`、**Hard** と **Review** に `opencode-route/frontier-heavy` を設定します。タスクの判断は Jev が行い、選ばれたルートがその後、プロバイダーを順に試します。

OpenCode は、リトライ可能なプロバイダーの失敗、クォータや認証のエラー、最初の出力期限の超過が起きると別の対象に移ります。完了したリクエストでも、設定されたレイテンシやスループットのしきい値を使って対象を劣化としてマークできます。クールダウンは OpenCode プロセス内のセッションで共有され、再起動後に復元されます。また OpenCode は、すべてのルーティング判断、試行（正確なエラーコードとメッセージ、タイミング、トークン数）、クールダウンをデータベースに記録し、後から分析できます。回答やツール出力が始まった後は、そのターンを再生することは決してありません。

OpenCode は各応答のレート制限ヘッダーも読み、プロバイダーが期間を使い切ったと伝えた対象からは、プロバイダーが拒否し始める前に通信を外します。

プールは、次に移る前に対象へ複数回リクエストしたり（`attempts`、既定では合計 2 回）、最初の対象が無反応なときに次の対象を開始したり（`hedgeAfterMs`）、対象のリクエストとトークンに上限を設けたり（`budgets`。タイトルのようなバックグラウンドのリクエストを含め、OpenCode がその対象へ行うすべてのリクエストを数えます）、記録した履歴をもとにエージェントが調整したりもできます。これらは OpenCode のルートオプションです。設定リファレンスを参照してください。

スケジュールは、決めた曜日や時間帯に対象の重みを変えます。たとえば、プロバイダーのピーク時間帯にそのプロバイダーへ送る量を減らせます。プールごとのスケジュールは **設定 → ルーティング → モデルプール** の各プールの詳細オプションにあり、プール一覧の下の **全プール共通のスケジュール** では、すべてのプール、または指定したプールだけで、一致する対象を変更します。各スケジュールには、曜日、日付、開始と終了の時刻、タイムゾーン、そして重みに掛ける係数か、重みを置き換える値のどちらかを指定します。時間帯の外では設定どおりの重みが使われます。OpenCode は、プロジェクトの `opencode.json` など、ほかの設定ファイルにあるスケジュールも適用します。設定画面ではそれらを読み取り専用で、編集先のファイル名の下に表示します。

各プールは、何のためのものかも書けます。**設定 → ルーティング → モデルプール** でプールを開き、**説明** に「多くのファイルにまたがる長いリファクタリング。遅い。一番コストがかかる」のような 1 行を、**詳細** にそのプールを使うべきときと使うべきでないときを書いた段落を入力します。カテゴリのモデルがプールの場合、Jev はそのカテゴリの説明と合わせて両方を読みます。OpenChamber はそれらを `opencode.json` のルートに `description` と `details` として保存します。OpenCode はこの 2 つのキーを無視するため、ファイルを OpenCode の JSON スキーマでチェックするエディターは警告を出すことがあります。

Jev はカテゴリの名前と説明を読んでプロンプトを振り分けるので、説明は指示として働きます。そのカテゴリに入るものと入らないものを書いてください。カテゴリは編集、オフ、削除、追加ができ、気が変わったら組み込みのカテゴリを元に戻せます。Auto には、オンのカテゴリが 2 つ以上必要です。

### どのセッションが対象を共有しているかを確認する

ある対象のプランを使い切ると、その対象上のすべてのセッションが一斉に切り替わり、それぞれ空のプロンプトキャッシュからやり直します。**設定 → ルーティング → モデルプール → プールの状態** では、各プールの対象ごとに、直近 15 分間にその対象を使ったセッションの数が表示されます。2 つ以上のセッションが同じ対象を共有していると警告が出ます。

そこで対象を自分のプランに紐づけると、予測が表示されます。その対象の最近の使用量を、同じプランに紐づいた他のすべての対象の分と合わせて、プランのクォータ期間に換算したものです。リクエスト、メッセージ、トークンで数える期間には予測が出ますが、ドルやパーセントで数える期間には出ません。この数値は直近 24 時間の OpenCode の通信から出した推定で、OpenCode の外での使用は含まれません。重み付けまたはラウンドロビンのプールでは、期間の 70% 以上に達した対象に **重みを下げる** ボタンが表示されます。押すとその対象の重みが半分になり、新しいセッションが他の対象に流れやすくなります。

## 送信したときの流れ

1. OpenChamber が、あなたのメッセージと直近のいくつかのターンの短い抜粋を Jev に送ります。
2. Jev がカテゴリを選び、どれくらい確信があるかを返します。
3. セッションがそのカテゴリのモデル、思考レベル、エージェントに切り替わり、メッセージが送信されます。

メッセージは毎回振り分け直されるので、ちょっとした質問には安いモデル、次の依頼にはいちばん強いモデル、ということも起こります。入力欄には **自動** と表示されたままで、エージェントと思考レベルの選択は隠れます。どちらもカテゴリが決めるからです。

次の場合はフォールバックモデルが答えます。

- Jev の確信が足りない（60% 未満）
- Jev が失敗した、または 4 秒以上かかった
- カテゴリに専用のモデルがない

モデル選択で具体的なモデルを選ぶと、そのセッションは Auto から外れます。戻すには、もう一度 **自動** を選びます。**設定 → セッション** で、新しいセッションの既定を Auto にすることもできます。

## プラン、使用量、レビュー

**設定 → ルーティング → プランと使用量** には、レビューでは測れないものが保持されます。あなたのサブスクリプションとそのクォータ期間（名前、単位、上限、期間の長さ、リセット方法）、料金と有効期限、各プランを最後に確認した日付と確認元、モデルごとのコスト区分（`plan`、`common`、`medium`、`high` と、それをカバーするプラン）、各プールが何のためのものか、使用感についてのメモです。メモは書いたとおりに保持され、書き換えられることはありません。「Claude がすぐ尽きた」「月末にはいつも GPT が余る」といったことに使ってください。レビューは使用履歴と照らし合わせてメモを評価します。

2 つのボタンは、送信するだけのコマンドを用意した新しいチャットを開始します。

- **ルーティングを確認** は `/routing-review` を実行します。ルートの履歴（リクエスト、トークン、コスト、セッション、どのプールがどのプロバイダーとモデルを使ったか、または飛ばしたか）、プランの記録、メモを読み、変更を提案します。具体的な変更を承認するまでは何も変わりません。
- **プランを更新** は `/plan-update` を実行します。詳細が不足しているプランや、最後の確認から 1 か月以上たったプランを見つけ、必要な少数の項目をたずね、あなたの回答を記録します。

記録は OpenCode のデータディレクトリに `plans.json` と `plan-notes.jsonl` として置かれ、その内容が期限切れになることはありません。履歴も保持されます。`route_usage` はその任意の期間を読むことができます。

## 使える場所

Auto は OpenChamber サーバーで動きます。デスクトップアプリ、Web アプリ、そしてそのどちらかに接続したスマートフォンで使えます。VS Code 拡張機能は OpenCode と直接やり取りするため、Auto はありません。
